# Native subscription bootstrap (development only)

The public upstream contract is [NVIDIA/OpenShell commit 1905069948f96921daf88bffb160dceb9ac2a307](https://github.com/NVIDIA/OpenShell/commit/1905069948f96921daf88bffb160dceb9ac2a307), specifically `examples/codex-app-server/{README.md,codex.yaml,start-codex-app-server}`. It predates the downloaded September 25 development binaries. Their CLI exposes `provider refresh configure` with `oauth2-refresh-token` and secret environment material.

The gateway holds real access/refresh credentials. The sandbox receives opaque access/account handles; vanilla Codex reads them from a private `auth.json`, with `auth_mode: chatgptAuthTokens`, empty refresh token, and a synthetic locally parseable ID token. The gateway refreshes access tokens using the Codex public OAuth client ID `app_EMoamEEZ73f0CkXaXp7hrann`. The launcher does not log in, call a model, provision a provider, expose a network listener, or use `inference.local`.

`symposium-subscription-app-server` is installed at `/usr/local/bin/symposium-subscription-app-server` in the disposable seat image. The controller invokes it with no arguments after establishing the seat Landlock boundary. It validates canonical `/sandbox/.symposium-seats/<64 lowercase hex>/.codex`, traverses directories without following symlinks, requires owner-only 0700 directories, atomically replaces only owned single-link 0600 auth files, and uses `os.execve` for native stdio/signal behavior. Raw access tokens and unbound aliases are refused. The environment allowlist removes API keys, provider credentials, injected Python settings, and host auth paths; only supervisor proxy/CA settings and basic locale are retained.

Access handles must be stable `openshell:resolve:env:s<64 hex>_CODEX_AUTH_ACCESS_TOKEN`; account handles can be stable or revision-bound `openshell:resolve:env:v<N>_CODEX_AUTH_ACCOUNT_ID`. These shapes come from `crates/openshell-core/src/secrets.rs` and `provider_credentials.rs`. Format validation is not attestation of the handle issuer.

Production remains closed. Refresh status proves lifecycle/expiry state, not the real ChatGPT identity behind an opaque handle. `account/read` sees the synthetic ID token, so its email or account metadata cannot independently prove the selected seat account. Admission still requires trusted host-side evidence binding the expected account to the exact gateway/provider identity and revision. The runtime must reject missing or stale evidence before starting a turn. Logging in inside the sandbox would put raw OAuth credentials in its filesystem and does not satisfy this privacy contract.

## Public identity contract audit (September 26, 2026)

Read-only inspection of the pinned upstream source confirms why a host verifier cannot yet be implemented from the public inventory and refresh-status APIs:

- [`redact_provider_credentials`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/grpc/provider.rs#L49-L64) masks credential values and clears internal credential handles. Provider names, configuration, labels, and resource versions identify a gateway record, not the ChatGPT principal that authorized it.
- [`ProviderCredentialRefreshStatus`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/proto/openshell.proto#L2225-L2255) returns provider identity and lifecycle/error metadata. It does not return the authenticated ChatGPT principal or authorization epoch. A healthy refresh therefore cannot establish ownership.
- The gateway already maintains a private [`authorization_epoch`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/provider_refresh.rs#L63-L83), regenerated on explicit reconfiguration and preserved across access-token rotations. That distinction is necessary for rejecting a different login without rejecting routine refresh. The epoch is not exposed through refresh status.
- [`StaticCredentialBinding.workload_credential_handle`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/proto/openshell.proto#L2466-L2500) incorporates that epoch for supervisors. Its enclosing provider-environment response carries credential material; it is not a host-safe account attestation API. A handle observed in a workload also does not establish the initial real account identity.
- Provider resource version cannot substitute for the authorization epoch. Routine [`apply_minted_credential`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/provider_refresh.rs#L1252-L1290) updates the provider through CAS. Conversely, [`handle_configure_provider_refresh`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/grpc/provider.rs#L4790-L4857) persists replacement refresh material separately and updates the provider only when an explicit expiration was supplied. Reconfiguration can therefore change authorization without changing provider version; ordinary rotation changes provider version without changing authorization. Rejecting all revision drift breaks refresh continuity, while accepting drift based on healthy status loses the original identity proof.

An attended provisioning flow could establish the initial real identity from independently validated OAuth identity evidence and retain a host-owned receipt. The receipt alone would become stale after out-of-band refresh-grant reconfiguration. Enabling production needs a reviewed public contract that binds authenticated principal, exact gateway/workspace/provider, and authorization epoch, with revalidation at every execution boundary. Alternatively, a separately reviewed custody design must prove exclusive control over all grant replacement paths. Neither contract is supplied by the existing callback or by a boolean capability flag. Any upstream extension requires discussion and approval before implementation; no private gateway patch is assumed.

This audit used public source only. It read no real credentials and performed no provisioning, authentication, refresh, or model calls. No speculative verifier was added, and the production subscription gate remains closed.

### Unpatched alternative: exclusive host provisioning custody

The public [local mTLS authentication contract](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/docs/reference/gateway-auth.mdx#L33-L68) permits a dedicated gateway whose only management identity belongs to the trusted host provisioner. With no OIDC admin role configured, [every authenticated user is a platform admin](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/auth/workspace_authz.rs#L126-L145); sole custody must therefore cover the issuing CA as well as the one management client key. Supervisor sandbox identities are separate and do not authorize provider mutation.

A viable implementation must start a new gateway with fresh storage and a dedicated CA, require verified client certificates, disable unauthenticated and alternative user-authentication paths, and keep CA/client keys outside all sandbox mounts. The host service must own every provider and refresh-grant mutation and invalidate its receipt before changing a grant. A receipt may then survive automatic rotation of the same OAuth grant, but must not survive reauthorization, gateway replacement, or a service restart that cannot reconstruct custody provenance. Initial account identity still requires verified real OAuth evidence, never the synthetic sandbox ID token. This is a custody proof under the existing trusted-host threat model, not a claim that provider inventory proves identity. Until the provisioning and live custody checks actually exist, it does not authorize opening the gate.

Podman startup requires guest TLS material, so a certificate-only management identity is insufficient when a guest certificate chains to the management client CA. A supported alternative separates transport TLS from OIDC user authorization: explicitly disable `mtls_auth`, enable a private host-owned OIDC issuer, configure nonempty admin/user roles, and keep `allow_unauthenticated_users` disabled. Guest certificates then establish transport only. The host issuer serves public discovery/JWKS, retains its signing key privately, and issues no tokens over HTTP. Its key, audience, issuer URL, and gateway process lifetime belong to the custody proof.

The upstream [authentication chain](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/multiplex.rs#L845-L888) checks sandbox identities before OIDC, and its [principal selection](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/multiplex.rs#L984-L1025) rejects absent authorization when both certificate-user and unauthenticated fallbacks are disabled. Authentication errors do not fall back. A gateway with no authenticator chain has a development fallback, so launch verification must establish an active OIDC chain, not merely disabled fallback flags. [OIDC verification](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-server/src/auth/oidc.rs#L830-L868) pins signature algorithm, issuer, audience, expiry and subject before reading roles. Management and sandbox JWTs must use distinct keys and key IDs.

The CLI loads a private [`oidc_token.json`](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-bootstrap/src/oidc_token.rs#L5-L35) bundle; no bearer-token environment override was found in the pinned CLI. The bundle contains `access_token`, optional `refresh_token`, `expires_at`, `issuer`, and `client_id`, under the dedicated gateway's private XDG config. Its [TLS client](https://github.com/NVIDIA/OpenShell/blob/1905069948f96921daf88bffb160dceb9ac2a307/crates/openshell-cli/src/tls.rs#L420-L439) supports bearer authorization layered over client-certificate transport. Runtime admission still requires negative checks proving a guest certificate alone and a sandbox JWT cannot mutate providers, while the owned host token can; wrong issuer, audience, signature, expiry, and role must fail. Source inspection alone does not establish those runtime results.

The profile intentionally excludes API-key discovery and `api.openai.com`; it allows only subscription/refresh/experiment endpoints for `/usr/bin/codex`. No profile was imported and no live login, refresh, provisioning, or model call was performed. Run the offline launcher checks with `python3 docs/spikes/openshell-codex/subscription-launcher.test.py`.

The reviewed profile ID is `codex`, matching the runtime's required provider type. It is intended only for a separate disposable workspace; do not import it globally or replace an active profile. Admission must attest the exact reviewed profile content as well as the provider instance.

In [Codex 0.153.4 source](https://github.com/openai/codex/tree/rust-v0.153.4/codex-rs/model-provider-info/src), configured `model_providers.openai` cannot override the built-in entry (`entry(key).or_insert(provider)`). However, top-level `openai_base_url` can override its endpoint. The launcher explicitly clears that override: the pinned config loader filters empty strings, restoring the native ChatGPT URL `https://chatgpt.com/backend-api/codex`. It also pins `chatgpt_base_url` to the official default `https://chatgpt.com/backend-api/` for other ChatGPT requests. These flags and forced ChatGPT login are covered by offline tests; no guessed provider replacement is introduced. Directory traversal uses Linux `O_PATH` for ancestors so the launcher works under the existing Landlock restriction without granting directory reads outside the seat home.

The existing Vitest suite invokes these offline Python checks through `server/__tests__/symposium-subscription-launcher.test.ts`; CI needs Python 3 and fails if it is absent.
