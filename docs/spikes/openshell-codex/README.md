# Codex app-server in OpenShell spike

This directory contains only disposable-spike artifacts. It does not change the
Mitzo runtime, account profiles, or production services.

## Intended topology

One OpenShell sandbox is retained per Mitzo task workspace/Symposium. It holds
one or more cloned repositories under `/sandbox/workspaces`; collaborating
seats deliberately share that task data. The host-facing Mitzo controller owns
conversation metadata and approval records. A small bridge
starts `codex app-server` **inside** that sandbox and uses the app-server
`externalSandbox` policy on each `turn/start` (and direct command execution);
the policy is not a `thread/start` or `thread/resume` field.

The sandbox must receive only task-scoped capability material, not integration
write credentials. A shared sandbox is the execution trust boundary: seat roles
and prompt filtering do **not** make files confidential from another seat. The
trusted controller or gateway provider is responsible for model/integration
authorization; a separate trusted executor performs approved external writes.
Separate seat sandboxes are a future option only when the product requires
different filesystem trust domains.

## Files

- `openshell-policy.yaml`: deny-by-default test policy. It permits only the
  explicitly enumerated read endpoints after the operator extends it.
- `app-server-request.json`: representative thread then turn requests. The
  externally sandboxed setting is correctly turn-scoped; it is a protocol
  fixture, not an account call.
- `gateway-podman.toml`: local-only OpenShell override for an existing rootless
  Podman machine. It is preferred over the VM configuration when the machine
  and socket pass the preflight checks.
- `Dockerfile.codex-0.153.4`: disposable derived image that corrects the
  upstream base image's older Codex CLI before testing `externalSandbox`.
- `openai-keychain-spike-profile.yaml`: workspace-scoped provider profile that
  supplies the bearer placement metadata missing from the installed registry;
  it contains no credential value.
- `openshell-openai-api-policy.yaml`: narrow inspected OpenAI Responses policy.
- `google-workspace-spike-profile.yaml`: delegated-refresh profile that injects
  the gateway placeholder through GWS 0.18.1's supported
  `GOOGLE_WORKSPACE_CLI_TOKEN` environment variable. Credential values remain
  gateway-owned and are not copied into the sandbox filesystem.
- `app-server-live-turn-probe.mjs`: real model/tool-loop marker probe. The
  built-in WebSocket route remains blocked; the custom inspected HTTPS provider passes.
- `mitzo-transport-live-probe.ts`: drives a live turn through Mitzo's app-server
  client over OpenShell's bidirectional SSH proxy.
- `prepare-mgmt-seed.sh`: creates filtered task content plus a host-side
  baseline manifest; save-back is not implemented.
- `Dockerfile.mgmt-runtime` and `build-mgmt-runtime.sh`: local-only reusable
  Linux runtime image. The builder requires an immutable OpenShell base-image
  digest and rejects `latest`/`dev` output tags. Because MGMT's checked-in lock
  currently predates a declared dependency, resolution occurs only in the
  disposable build context; the host checkout is not rewritten.
- `synthetic-secret-probe.mjs`: presence-only placeholder/canary boundary probe.
- `run-disposable.sh`: creates a no-credential sandbox, performs harmless
  filesystem/network boundary checks, then deletes the sandbox on exit.
- `symposium-seat-fixture.*`: mocked two-seat contract showing separate
  account/model/context bindings and transcript provenance in one shared
  workspace. It is not a cross-provider live test.

Run the script only against an already working local OpenShell gateway. It
does not configure providers or transmit secrets.

## Acceptance boundaries

The app-server schema generated by installed `codex-cli 0.153.4` includes
`{ "type": "externalSandbox" }`. This proves the protocol capability, not
the outer OpenShell enforcement. A pass requires the disposable command to
finish with `POSITIVE_FILESYSTEM=pass`, `POSITIVE_NETWORK=pass`, and
`NEGATIVE_NETWORK_POLICY_DENIAL=pass` while the sandbox exists. The negative
control requires the proxy's explicit `policy_denied` response, so an unrelated
DNS/TLS/connectivity failure cannot count as a denial. An authenticated account
test must still be performed without mounting credential material.
