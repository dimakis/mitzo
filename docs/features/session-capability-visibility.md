# Session Access capability visibility

As of 12 November 2026, this slice extends **Links & access** with a collapsed
**Capabilities** disclosure. It reuses the approved compact sheet, native
disclosures, quiet fact rows, shared semantic tokens and existing refresh/focus
owners. It changes no Chat settings hierarchy or approved-design revision.

## Support and verification

The authenticated Access projection consumes the retained runtime binding and
the captured agent-tool selection. For guarded Local Mac Claude and Codex, the
existing executable tool catalog supplies Mitzo helper support. A helper can be
supported by the route, unsupported, excluded by the published agent profile,
or blocked by the active skill restriction. An absent captured selection is
unknown, never an unrestricted default. OpenShell, legacy bindings, other engines,
lost owners and identity mismatches do not acquire a qualified helper inventory.

Support is configuration evidence. It neither inventories native engine tools
or configured MCP tools nor proves a helper callable, a service attached, an
approval granted, or an operation successful. Executors retain their existing
account, profile, workspace, cancellation and permission checks. This view makes
no probes, model calls, service requests, grants or runtime registrations.

`projectRuntimeReadiness` remains the sole observation projector. Its existing
session/account/profile/model/binding/owner-generation/task-root checks and
timestamps are preserved. The consumer renders process, tool, executable and
individual service-operation observations independently. A successful list cannot
verify document-text access. Each operation expires using its original timestamp;
expired results and failed refreshes retain explicitly earlier observations.
Unknown, scope-mismatched and invalid evidence cannot become success.

No production runtime adapter supplies capability measurements in this slice.
Consequently, the ordinary application continues to report operation verification
as unknown until an owning adapter supplies qualified evidence. The observation
rendering path is exercised offline; it is not a claim of live service qualification.

The shared protocol owns the Access types and helper-support schema, so the
frontend does not import server implementation types. Present readiness and helper
fields validate on receipt; older servers may omit them. An invalid refresh keeps
the last observation and displays the existing failure/retry state.

Unexpected Access reads return a sanitized `session_access_read_failed` diagnostic
with stage and conversation identity. The existing structured logger preserves
trace correlation and classified cause information without exception text, stack
paths or sensitive payloads.

## Validation and delivery

Implementation starts from accepted `01ea649542ea225343396b743a77e77510a52264`,
whose parent is the first parity slice, PR #1319 (`8175174b`).

The first endpoint regressions failed before implementation because helper-support
evidence was absent. Focused regressions cover the actual authenticated router,
catalog/profile composition, SSR consumer, mounted Access consumer, lost owners,
invalid evidence, stale refreshes and per-operation expiry. Existing readiness and
catalog tests remain unchanged. Design, motion, lint, formatting and source
fingerprint checks retain their original contracts.

The intercepted `session-access` browser fixture adds the capability disclosure
at phone/desktop widths, dark Mint/System and light Teal/Georgia with larger text,
44px summary controls, scrolling, keyboard opening, Escape/focus restoration,
stale failure retention and an unsent composer draft. All traffic is intercepted.

Local package builds and focused component type checking pass under the required
1 GiB heap cap. Full frontend type checking and Vite bundling each exceeded that
cap before browser execution. Full combined builds, browser execution, screenshots
and visual acceptance therefore remain CI/review evidence to acquire. No higher
heap, staging, production fallback, live model/service qualification, merge or
deployment is claimed.

Work reuses readiness slice `dec417f605a93232` and capability baseline feature
`1a3ad6c5-36b0-4744-9ea1-7bd8c18f253b`. Reviewed dedicated Telos role/session setup
remains unavailable in the exposed catalog; implementation provenance is not a
worker-binding receipt. Broader feature and outcome acceptance remain separate.

The broader `ordinaryCodexCapabilities` inventory in
`server/ordinary-local-codex-entry.ts` currently converts an inventory exception to
an absent route in `availableInventory`, without a structured cause diagnostic.
This slice does not call that inventory or alter admission. The adapter-evidence
follow-up should retain a sanitized route/stage diagnostic there while preserving
the intended independent-route fallback and all account/cancellation checks.
