# Bounded task execution for ordinary Claude

Ordinary Local Mac Claude can select the existing `TaskExecution` helper and
invoke it through the SDK permission callback and managed MCP handler. Default
and explicit profiles support personal Claude, Vertex and qualified Anthropic
Messages API accounts. An excluded tool has no handler admission or task-routing
guidance. Account/runtime support remains subject to the canonical task owner.

Status requires the verified ordinary owner. Authorization reuses eligible
existing development/repository consent or presents one bounded task decision
with the selected accounts, roots, repositories, network scope and expiry.
In-scope command/test/build/local-commit and repository-read variants reuse that
grant. The executor rechecks operator, account, workspace, profile selection,
skill policy, cancellation, revocation and expiry. Ask mode cannot authorize or
execute task work. A grant never authorizes native Bash, credentials, publication,
merge, deployment or unrelated effects.

The handler checks its actual wire name against the original command's frozen
tool ceiling before dispatch and through the existing effect authority. The
ceiling can only restrict the profile and existing operation permission. FIFO
successors, steering and recovered commands cannot replace the original query's
ceiling. See [the SDK command boundary](restricted-skills-sdk-command-handoff.md).
Public restricted-skill execution remains unavailable pending trusted admission
qualification; internal enforcement tests do not enable that product surface.

Successful SDK completion records flow to the existing shared notification
center. The SDK query loop does not send independent ntfy/Pushover alerts when
that owner is installed. Existing preferences, quiet hours, preview privacy,
delivery channels and deduplication remain authoritative. A standalone consumer
without the shared owner retains legacy completion sends; failed sends produce
a correlated diagnostic. Notification delivery never grants consent.

Offline tests use real SDK MCP transport, task storage, permission handling,
canonical native-executor fences and the shared notification center. Only the
command process effect, provider and push transport are synthetic. Coverage
includes one approval/alert for two command variants, default/selected/excluded
profiles across the three SDK account routes, denial, Ask/account/owner changes,
expiry/revocation/cancellation and uncertain-receipt replay refusal. API startup
and continuation also exercise actual `canUseTool`/`PreToolUse` options. Completion
tests exercise the real query-loop consumer and standalone fallback.

Accepted information/Telos helpers retain their existing owners. Coordination,
services, runtime reporting, device ownership and optional SDK controls keep
their separate delivery scopes; this document does not claim full parity.
Current reconciliation and test limits are recorded in
[the delivery evidence](../evidence/claude-parity-1342-reconciliation-2026-11-14.md).
No live model/account/service write, device delivery or deployment is qualified
by the synthetic tests.
