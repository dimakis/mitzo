# Canonical ordinary delivery evidence

`server/__tests__/telos-canonical-journey.test.ts` exercises CT06 with the accepted
MGMT fresh schema and real work, event, workspace, runtime, task and artifact
owners. Account/login/native bytes, external repository authority, native RPC and
provider effects are synthetic. There is no model call or live runtime target.

The journey starts from a synthetic planning origin and retained material. The
advisor saves an exact child through the canonical owner, including required
observed timestamps, initial history and an idempotent receipt. The same real
EventStore owns planning capture, lead setup and worker execution. Mounted role
HTTP routes and the public client review/confirm the lead with its exact display
reference, then the authenticated lead delegates only the selected child.

The worker has an independent repository workspace and conversation, pinned to
the selected base commit. Creation returns `chat_ready`/`not_started` with one
pending task and no ordinary command or native dispatch. Replay retains the
same worker/task and leaves a sibling untouched. The test verifies complete
context/task hashes and the worker's retained presentation.

An explicit command enters `OrdinaryLocalCodexOwnedRuntime.admitPreparedFirst`.
Its real admission/dispatch owners consume the original preparation, construct
and verify the actual Git checkout, and deliver the retained mandate. The fake
provider effect takes that exact dispatched command lease, saves a report through
the existing artifact router, attaches its receipt through the exact task guard
and handler, and reports completion through the worker tool callback. The task
becomes `pending_review`; the Telos child stays active.

Explicit verification reads the saved artifact and its digest before approving
the existing task. The lead then records evidence-backed Telos completion through
the existing item route. The parent and sibling remain active. This is offline
integration evidence, not automatic evidence verification or user/live acceptance.

Authoring diagnostics are retained separately. The first fixture incorrectly
supplied an already allocated repository; the real owner refused reuse. A second
probe inspected the task directory before explicit command admission, although
`chat_ready` is a reservation rather than an executable checkout. Another used
the wrong preparation DTO field; the actual field is `workspaceId`. These are
fixture corrections, not failing-before product claims. The corrected complete
journey and its final command-lease/artifact checks pass; package and scoped
TypeScript checks pass.

The shared native-runtime test fixture exposes its existing command factory and
fresh repository preparation independently of ordinary session allocation. The
existing sibling helper reuses that repository helper. No production allocator,
scheduler or provider route is added. CI now retains Telos setup/context captures
for the independent UI/acceptance lanes; a future CI run must produce them.

The source remains a local candidate until its own current-head CI, reviews and
acceptance gates pass. Full S5a acceptance remains open. S5b runtime implementation
still requires accepted S5a; this repository-backed fixture is never evidence for
a repository-free workspace.
