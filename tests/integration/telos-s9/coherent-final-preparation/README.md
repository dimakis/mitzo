# S9 coherent App source compositions

This private source candidate is based on Core `7da7394fee293baea241aa0e4bb21ee9b726120e`
(tree `4b68782ebc73d8562bae3a5d484e410df520c2de`). It adds dedicated acceptance
files only. The accepted baseline remains merged PR1081 / `3f6c6ae`; this candidate
has not been accepted, built, loaded or executed. See `CONTRACTS.json` for exact
source bindings, retained test donors, scope and dependencies.

`coherent-app.contract.ts` contains two concrete runnable outer cases, CT06 repo
and CT09 non-Git. There are no skips, guessed future methods or placeholder cases.
The explicit configuration selects only these two cases. An internal carrier runs
one selected initial App composition per outer case; it is not another CT row or
independent acceptance result.

Each case captures an immutable origin packet through the real App, reviews
advisor context, previews/saves one child with exact retry, reviews the current
brief and source readiness, starts a real lead, and allocates exactly one worker
through its original native tool callback. Real workspace owners supply distinct
roots. Repo roots retain the actual synthetic Git main; non-Git task roots must
have no `.git`. Provider file/Git writes are explicitly labelled fake external
worker output generation. The original native Save/Read, Task MCP, Task review,
operator artifact byte read, approval, and original lead's canonical child then
Outcome completion remain real, with exact receipt retry and retained UI reload.

The repo case then reviews a separate explicit publication profile and replaces
the lead through the real role owner. The original report lead remains the actor
that verified canonical completion; the new current publication lead performs
its own physical first command. The real native capture, selected credential
custodian/capability, existing Once endpoint and publication owner supply authority.
The existing 1048 test fixture supplies fake remote command effects only. Its
pins, adapter and dispatch helper never supply application authority. A hold is
introduced after Once and before final effect admission, followed by release and
a fresh request. Remote main advances during the next Once. A fake lost mutation
reply must leave uncertainty; exact observation retries recover one durable
receipt without another permission or mutation. Passive observers retain actual
private record-owner returns; the public runtime result is not widened or cast.

The initial App lives in a dedicated process. Its successful exit and independently
observed worker PID absence precede cold App construction on the same files. The
cold App uses original imports, owners and signed synthetic operator auth. Real
HTTP reads and the original worker command retry check task/output/source and
workspace retention, canonical completion and publication receipt persistence,
with no provider launch. No parent DB is queried after its owners close.

Cleanup responsibility transfers through a private PID/root marker before App
import. Setup and oracle failures still await process reaping; an unexpected
surviving worker preserves its root and ownership record and fails. Cold teardown
awaits child close and retains the original error alongside cleanup failures.
The initial App's idle-close API is not used as a general shutdown after installing
an orchestrator. Manual per-store cleanup is not claimed to close all App owners;
the OS process exit supplies that fence.

The five helper implementations from `4c9b3c37` are byte exact. Reused J6 and final
worker test support is also byte exact, including the pinned accepted MGMT read
CLI bundle. Real exclusive creation of the canonical/events/tasks files precedes
any SQLite owner, and accepted canonical fixture DDL/WAL initialize that same file.
There is no database birth recreation or caller-supplied availability/permit.
